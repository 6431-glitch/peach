# ADR-0138：用户可触发的账本备份与恢复

- 状态：已采纳
- 日期：2026-11-04
- 相关：ADR-0040、ADR-0052、ADR-0091

## 背景

账本是唯一真相源。此前只有写入前的自动备份（`ledger.pre-<用途>-<时间>.db`）与清退规则，设置页只能清理旧备份。想回到某一份备份，只能停服务、手工换文件，还要自己处理 `-wal`／`-shm`、结构版本和任务记录。

恢复是第一个由用户在界面上触发、整份替换账本的动作，需要定下替换方式、前置条件和中断后的处理。参考了 javm（MIT）`docs/decisions/0026-library-recovery.md` 的行为：Backup API 分页复制、通过检查才转为正式备份、恢复前另存当前库、恢复中断留标记。

## 决策

1. **立即备份**：后台任务（`ledger-backup`，进任务中心）用 SQLite Backup API 分页复制到 `ledger.pre-manual-<时间>.db.part`，`integrity_check` 为 `ok` 才改成正式文件名，没通过就删掉。命名与保留沿用自动备份：同在账本目录，按 `peach.ledger_backups` 的「最近 5 份、24 小时内、比账本新」三条规则清退。
2. **恢复的前置条件**：只在写入端执行；数据目录里没有别的任务在跑（`update_tasks.running`，与安装更新同一判据）；恢复期间用安装预约挡住新任务。备份先过完整性检查，复制到暂存后按当前程序的迁移目录检查结构：来自更新版本的备份拒收，较旧的备份在暂存里迁到当前结构，再查一次完整性。这些检查都在动账本之前完成。
3. **先另存再替换**：当前账本另存为 `ledger.pre-restore-<时间>.db`，同一套保留规则。
4. **替换方式**：不换文件，而是经 Backup API 把暂存整库写进在用的账本。服务的连接都是按请求开关的；写入期间账本上是一个写事务，别的连接照常读旧内容，进程中途退出时事务回滚，账本仍是原来那份。Windows 上换文件会撞上打开的句柄，WAL 模式下还会丢掉 `-wal` 里已提交的内容。当前账本已经坏到 SQLite 打不开时才退回整份换文件。
5. **运行记录不随备份回退**：替换后用另存的那份覆盖 `task_run`（任务历史和这次恢复自己那一行），`ledger_revision` 取两边较大值再加一，聚合缓存不会撞上旧版本号；随后清掉服务的读缓存。
6. **中断标记**：写进账本之前在账本目录留下 `ledger.restore.json`，写完才删。服务启动与 `peach migrate upgrade` 在打开账本前先处理它：当前账本完整就保留；不完整或不在了，用暂存里迁好的备份补完；暂存也不能用，就退回另存的那份。账本不在时绝不交给后面的步骤，否则会被当成新装建出空账本。结果写进 `ledger.restore-result.json`，设置页显示。
7. **坏账本也能进入恢复**：账本读不出来时任务中心那张表也读不出来，恢复改用一个不进任务中心的后台任务，查忙只看登记文件与锁。

## 代价

- 恢复期间进来的写请求会等写锁，拿到后写进恢复后的账本；定时任务撞上预约会排队，文案沿用「等待安装完成后继续」。
- 恢复后，依赖账本的确定性补修（升级补修）在下次启动时才按版本补上。
- 页面大小与当前账本不同的备份不能在服务运行时恢复，会直接拒收。
- 双机复制时，恢复后的账本照常由写入端发布，读取端随下一次同步拿到；读取端不能恢复。
