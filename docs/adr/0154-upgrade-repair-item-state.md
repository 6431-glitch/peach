# ADR-0154：升级补修逐片状态进状态表，延后与退避重派

- 状态：已采纳
- 日期：2026-11-08
- 关系：补充 [ADR-0126](0126-upgrade-effective-repairs.md) 第 4、5 条；不改变规则版本与派发边界

## 背景

ADR-0126 让升级补修把派发记录写进 `ledger_upgrade_repair` 的回执 JSON，失败项等用户显式重试。生产实例跑了几轮后：

- 回执长到 2.5 MB，队列里有 1.8 万条键，其中 1.5 万条对应的任务行早已清退。每分钟的调度逐条查这些任务的状态，一轮 55–74 秒，服务启动还要等首轮跑完才监听。
- 显示尺寸补测每完成一部片，就在写锁里整份解析、重写回执。
- 影片补全每部片单独跑一次 `process_library`，每次整份读写十几 MB 的候选表。
- 挂载掉线、来源冷却、容量触线一律按失败结算，此后再不重派。11-06 挂载掉线时，42 分钟里每秒失败一条，留下 5,856 条失败。

## 决策

**一、逐片状态进状态表。** 迁移 0053 建 `ledger_upgrade_item`，每条规则每部片一行：状态、文件世代、所属任务、失败次数、重派时间与结果。显示尺寸补测的目标、文件世代与完成结果都在这里，完成行与测量同一事务提交。回执只留规则、备份与还在跑的队列。

**二、队列结算。** 每轮调度先把已结束的影片补全移出回执队列，结论写进状态表，防重复派发改看状态表。只改两种行：本版派发时记下、仍归这一轮任务管的，和旧版留下、表里没有结论的；处理器自己写过结论的不动。任务行已被清退的按完成算，因为后继的清退只删成功与取消的行。

**三、延后与退避。** 影片所在目录读不到、计费来源未确认、资料来源冷却时，这部片记为延后，到时间自动重派，不算失败、不计次数。本版派出的失败按退避自动重派，10 分钟起翻倍、最长一天，连续失败五次后只等用户重试。容量触线时整批暂停，撞线的那一条挂回队列，用户重试后接着跑。

**四、旧失败等用户决定。** 旧版本留下的失败结算进状态表时不带重派时间，只在用户点「重试」后重新派发。是否批量重派由用户决定，升级不自动带起。

**五、影片补全合批。** 同一规则的影片补全按 16 部合成一条后继，共用一次 `process_library`，每部片的结论各自写进状态表。回执队列仍按每部片记，排队配额按片数算，最多 64 部。

## 后果

- 回执只随还在跑的队列变化，不再随馆藏增长；调度每轮只查活着的任务。
- 老用户升级后无需操作：重启时迁移建表，`prepare` 把旧回执的逐片字典搬进状态表，首轮调度结算旧队列。搬迁可重复执行，已有的行不动。
- 任务中心里一批影片补全显示为一行，标题写首部片名与片数。
- 状态表随账本备份与恢复；读取端在同步到迁移后的账本前没有这张表，读进度时按零计。

## 验证

`tests/test_upgrade_repairs.py` 覆盖旧回执搬迁的幂等、队列结算后不重派、旧失败只在重试后派发、挂载与冷却延后、退避与次数上限、容量触线挂回队列和合批结算；`tests/test_migrations.py` 覆盖迁移版本。
