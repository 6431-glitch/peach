# ADR-0141：复核页逐条列出并撤回核查结算的自动写入

- 状态：已采纳
- 日期：2026-11-04
- 关系：补充 [ADR-0139](0139-verification-differences-settle-by-rule.md) 的撤回入口；沿用 [ADR-0052](0052-entity-results-land-when-evidence-is-sufficient.md) 的「能按来源与批次整批撤回」、[ADR-0138](0138-user-triggered-ledger-backup-and-restore.md) 的账本备份

## 背景

ADR-0139 让核查差异按确定判据自动落库，撤回入口是 `scripts/revert_auto_landing.py --source <规则名> [--batch …]`。升级后结算一次存量，真实账本 2026-11-04 写下标签并集 829 行、官方覆盖 100 行。用户要撤回就得进终端、读懂规则名与批次号，再记得加 `--apply --backup`；单人自托管的普通用户不该为此进终端。

人要判断的是「哪部作品被写成了什么」。规则名与批次号是撤回的依据，不是判断的对象：同一天那 100 行覆盖还分在 20 个批次里，覆盖的批次号取的是每个小事务的写入时刻（`rule@<now>`），一次结算跨了两分钟。

## 决策

**一、撤回逻辑只有一份。** 脚本里的计划与执行挪进 `peach.auto_landing_revert`：`plan` 只读，`apply` 在调用方的事务里写账本，`remove_files` 等提交后再删盘上文件。脚本只剩参数、打印与备份；复核页调用同一个 `plan` 与 `apply`，被人改过或已删除的资产照旧记在 `changed` 里不动。

**二、一行一条写入，作品与写入内容是主列。** 「元数据字段」分类下的「自动写入的资料」逐条列出 `adr-0139-official-replaces-verified` 与 `adr-0139-verified-tags-union` 仍在的决定：作品（封面、番号、标题）、写入（字段、写成的值，以及原值或补上的标签），规则与时间叠在最后一列。勾选一条、几条或全部都可以撤；按时间排序后连续勾选，就是撤某一次结算。

**三、只放行这两条规则。** 两条规则只改账本、不删文件，决定里存着撤回要用的全部依据。别的自动落库来源（种子、别名、样张、无番号封面……）有的要删盘上文件、有的要按任务行认批次，仍只在脚本里撤。接口只认列表里有的决定键，查不到就拒绝。`plan` 为此多两个参数：`item_keys` 只收窄核查结算那一类，`files=False` 不扫标识与封面目录。

**四、先预览，再按同一份计划写。** `GET /api/review/auto-landings?items=…` 返回逐条要改回的值、要删的标签、不动的资产和计划摘要 `token`。`POST /api/review/auto-landings/revert` 在写锁（`BEGIN IMMEDIATE`）里重算计划，`token` 对不上就拒绝；对上了先用 SQLite Backup API 留一份 `ledger.pre-auto-landing-revert-<时间>.db`（与标签管理同一做法，完整性检查与清退留给账本备份那一轮，不在写锁里多等），再撤回。回执写出备份文件名与被跳过的作品，作品可以点开核对。

并集决定按决定撤：一条决定之后又补过一次时带着两个批次，撤这一条就删掉它两次补的标签，预览逐个列出。

**五、一次结算一个批次号。** 覆盖的批次号改用与并集同一个运行时刻（`<规则名>@<本机时间>`）。2026-11-04 已写下的 20 个覆盖批次保持原样，时间按批次号里的 UTC 时刻显示。

## 理由

- 撤回是 ADR-0052 落库的前提。入口只在终端时，「能撤回」对普通用户只是纸面上成立。
- 判断撤不撤看的是作品和值；按批次列出时一行背后是几十部作品，看不出写错了哪一条。逐条列出也让撤回不必连带同一批里写对的那些。
- 一份实现让网页与脚本的判据不会分叉：人工字段的保护、被改过就不动、决定一并删除，都只在一处。
- 写锁里重算加 `token`，确认弹层里看到的就是将要写的；中间又有一轮结算或人工修改时，提示重新预览而不是悄悄多撤或少撤。
- 白名单而不是全部来源：页面上看不到、预览也列不出的来源，不该经网页触发删除文件。

## 被否决的方案

- **按批次列出，一行是一批。** 主列只能写规则名与条数，人仍要点开预览才知道写了什么；2026-11-04 的预览先做成这样，用户指出主列应是写入的信息和作品。
- **网页列出全部自动落库来源。** 每种来源的写入存在不同的表和边车里，有的撤回要删盘上文件或重建旧行；逐一做成可预览的列表远超这次的需要，脚本仍覆盖它们。
- **把存量的 20 个覆盖批次合并成一批。** 要改写决定里的批次号，撤回依据随之变化；逐条列出之后批次号已不在主视图里。

## 后果

- 复核页「元数据字段」在有自动写入时多一张表；只读端按本机同步到的账本浏览，撤回由写入端闸门拒绝。
- 「账本备份」列表里多一种用途「撤回自动写入前」，按同一套保留规则清退。
- 撤回后决定被删，下一轮资料处理仍按同一判据判断，可能再次写入；改判据仍要先于撤回，弹层里写明这一点。
- `scripts/revert_auto_landing.py` 的参数与输出不变。
