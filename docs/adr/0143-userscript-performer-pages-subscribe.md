# ADR-0143：用户脚本在女优页订阅新作，只有名字时由 JavDB 确认唯一一人

- 状态：Accepted
- 日期：2026-11-05
- 关系：放宽 [ADR-0083](0083-feed-subscriptions-by-name-create-performers.md)「由查找结果直接建，
  不让用户勾」这一条否决，只限用户脚本的女优页；订阅源页签照旧由用户勾卡。订阅地址仍由服务端按
  JavDB 演员 id 与 DMM 女优编号现拼（ADR-0047、ADR-0135）。

## 背景

用户在 JavDB、DMM、MISSAV 等站浏览女优页时，想直接把她加入 Peach 的新作订阅，不必回到 Peach
搜名字、勾演员卡。三类页面带的身份不一样：JavDB 演员页地址里有站内 id，DMM 女优片单地址里有
女优编号，MISSAV 女优页只有名字。

另有反馈说订阅女优「搜不到」。按名字订阅只靠 JavDB 演员搜索，JavDB 冷却、限流或回登入页时
整条路都走不通，连库里认得出、已有编号的人也订不了。

## 决策

**一、脚本专用端点。** `GET /api/jav-browser/performer?source_url=…&names=…` 认人并回订阅状态，
`POST /api/jav-browser/performer` 订阅或取消。两者用浏览器添加的专用令牌，不收订阅地址。

**二、按页面编号认人。** JavDB 演员 id 与 DMM 女优编号（`dmm`、`r18dev` 同一套）已在谁名下就是谁；
没人持有时按页面名字认正名或唯一别名，认不出就新建她，并绑上这个编号。DMM 页没给名字时按编号向
DMM 问她的名字。这和用户在订阅源页签勾一张卡是同一件事：页面本身就是那个人。

**三、只有名字时由 JavDB 确认唯一一人。** 库里认得出、又已有编号的直接订。否则按名字到 JavDB
搜演员卡，名字对得上、且 `one_person` 判为同一个人的那几张才登记并订；同名不止一位或搜不到时
不猜，请用户到她的 JavDB 演员页订。用户 2026-11-05 要求这条路「能确认是一人才添加」。

**四、按名字订阅不被 JavDB 搜索卡住。** 订阅源页签的查找在 JavDB 搜不成时，如果名字认得出库里
已有编号的她，返回她并说明 JavDB 没搜成的原因，页面给出「订阅库里的她」。

## 理由

- ADR-0083 否决自动选卡，是因为输入的名字可能指同名的另一位。女优页的名字来自她本人的页面，
  再要求 JavDB 上名字对得上的卡只有一个人，挂错人的余地与用户在页签里看卡勾选相当。
- 编号比名字硬：有编号的页面不经搜索，JavDB 冷却时也能订。

## 被否决的方案

- **只有名字时也新建实体、等资料后继补编号。** 订阅要编号才拉得到新作，新建一位订不上的人只会
  多出一条空订阅。
- **MISSAV 页搜到多张卡时让脚本列出来勾。** 浮卡放不下卡片列表；同名多位时交给 JavDB 演员页，
  那里的地址自带 id。

## 后果

- `web_feeds` 公开 `subscribe_performer`、`fetch_new_sources`、`subscribable` 与
  `create_followed_performer`，人物页开关、订阅源页签与脚本端点共用。
- 按 DMM 编号新建的女优只有 DMM 片单一个订阅源，JavDB 演员页等资料后继绑上 id 后在下一轮补订。
- `tests/test_feeds_web.py` 的 `PerformerPageFollowTest` 钉住地址解析、三类认人与拒绝条件。
